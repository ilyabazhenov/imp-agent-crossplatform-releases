One app — a workspace and a door for other agents

Inside is one and the same thing: service tokens, 101 tools and the knowledge of how Jira, Bitbucket, Jenkins and TestOps actually respond. There are two ways in — through its own window, or over MCP from Claude Code, Codex and Cursor.

Both ways in lead to the same core. The only differences are who holds the model and where the person sits.

Role 1 · workspace

A view built for the task, not a generic chat over files

For whoever works in the IMP Agent window. Every service gets its own section: a red TestOps run, a review with its diff and comments, cluster pods and logs. The agent lives right alongside and takes on whatever you point at.

  1. Open a run in TestOps — the failures are already grouped by cause.
  2. One button sends the agent a brief with the run, the build and the branch.
  3. The agent reads the Jenkins log, the code and git history, and proposes a fix.
  4. The fix and the Jira comment happen only after you approve them in this same window.

Role 2 · MCP server

Your work services in your favorite agent — without a single token in its config

For whoever lives in Claude Code, Codex or Cursor. The app runs an MCP server on loopback, and the other agent gets the same tools. You don’t even have to open the IMP Agent window — the app just needs to be running.

Team catalog

How the team works — kept in one repository and delivered to both roles

Rules like “how we name PRs”, “where bugs go” and “what our jobs mean” used to live in one person’s settings, tied to a path on their disk. Now they go into a shared Bitbucket repository, and every IMP on the team reads it on its own. Rules change by pull request, just like code.

  1. pull requestA change in the cataloga new preset or a line in the rules
  2. review · mergeThe team agreedthe rule is merged into the catalog branch
  3. ≤ 30 minutesEvery IMP checks the commitfiles are re-read only after a new commit
  4. right awayWorks for everyonein their own window and in their Claude Code, Codex, Cursor

Yours adds on, it doesn’t replace

A team rule shows up in settings as a box above your own field, with its source: catalog · file · commit. Your own text is appended after it and never overrides the team’s.

Linked folders stay fresh on their own

Autotests and docs next to the project are no longer read as a snapshot of the last manual git pull: a clone in the linked-folders table has a sync checkbox and a schedule. While the agent is working, the folder is left alone.

What stays out of the catalog

Paths on disk and the command environment — that is knowledge about one person’s setup.

Why one app, not two

Both roles stand on the same foundation

A standalone MCP server would have to be given everything the app already has — and it still wouldn’t know how these services really respond.

Secrets

Tokens live in the system keychain. They are never copied into a client config or into environment variables.

Service knowledge

Bitbucket paging, Jira createmeta, Jenkins stage names, TestOps failure grouping.

Human in the loop

Risk judged by the arguments, a dialog with the diff, “always allow” — one rule for both ways in.

Company network

Corporate root CAs, fingerprint trust, per-host rate limits, a trace of every request.
